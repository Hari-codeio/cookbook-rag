TOOL DESCRIPTION DIFF, v1 -> v2
================================

v1 had TWO tools and their descriptions overlapped: search_recipes said it
returns "matching recipes with their ingredient lists", and scale_recipe said it
returns "a recipe's ingredient list with the amounts adjusted". Both promised the
ingredient list, so nothing in the text told the model which one to reach for.

v2 fixes that in three ways, none of which is a bigger model or a sterner system
prompt:

  1. each description opens with ONE capitalised verb - FIND, MULTIPLY, REPORT -
     so the single job is the first thing read
  2. each ends with an explicit "Does not ..." naming the other tools' jobs, so
     the boundary is stated rather than left to be inferred
  3. the new tool's `allergen` parameter is an ENUM of the nine values that
     actually appear in the corpus frontmatter. A wrong value is now rejected by
     the schema instead of silently matching nothing and coming back clean,
     which would have read as "no allergens found"

The third tool, get_allergen_profile, takes a LIST OF INGREDIENT NAMES rather
than a recipe_id. Keyed on recipe_id it could only answer "what is wrong with the
original"; the list form also answers "is the replacement I just chose safe",
which is what a cascade needs, and it still does exactly one thing. It
deliberately does not choose the replacement, because choosing is the only part
of this task that is not fixed and the verdict depends on being able to see it.
