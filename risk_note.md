**Who wrote it:** the content team, not us (vendored at `mcp_servers/ingredient_db`, commit `f0e0497`); no signature or pinned hash, and its self-reported `serverInfo.version` is the MCP SDK's `1.30.0`, so nothing identifies which build we run.
**What it can reach:** it runs as a child process with our OS user's full file and network rights (the code only reads `ingredients.json` today, but nothing enforces that), and it receives every ingredient string our model sends it, which means user request content.
**What it logs:** every tool call, as timestamp, tool and the raw query string, to `out/ingredient_db_queries.log`, unrotated and unredacted, so user-typed text sits in plain text on disk.
**What a stolen token could do:** over stdio it has no token; anyone who can start the process can query it, and a tampered copy could return false "no allergen" flags that our agent would repeat to a user. Behind the bonus gateway, a stolen `menu-bot` token allows read-only lookups (nutrition denied) under our name in the audit log.
**Ship or don't:** ship behind the gateway (scoped token, one audit line per call) with the code hash pinned in review, but NOT as the sole allergen source: `get_allergen_profile` on our own server must still agree before a substitution is shown.
